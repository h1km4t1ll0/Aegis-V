# 19 — GCC 4.6.4 on Tilck (rungs `gcc1`, `musl2`, `gcc3`, `gcc4`)

Plan 5 (`docs/2026-10-30-gcc464-plan.md`), phase 1. Rung `gcc1` of the Tilck ladder (14-seed README, "Rungs on Tilck"): starting from `18-gmp-mpfr-mpc/artifacts/rootfs-gmp.tar` (tcc-m on musl, bash 2.05b as `/bin/sh`, make 3.82, coreutils, sed, grep, gawk 3.0.4, m4, flex 2.6.4, diffutils, findutils, tar 1.12, patch 2.5.9, binutils 2.30, gmp/mpfr/mpc in `/usr`), Tilck builds GCC 4.6.4 from Ekaitz Zárraga's RISC-V fork with tcc: C only, `--disable-bootstrap`, its own top-level `configure`, `make`, `make install` into `/usr/gcc1`. That compiler is **gcc-1**. `/usr` goes back as `artifacts/rootfs-gcc1.tar`, the rootfs of rung `musl2` (phase 2).


`RUNGS["gcc1"]` (`src/scripts/tilck.py`): rootfs `18-gmp-mpfr-mpc/artifacts/rootfs-gmp.tar`, steps `gcc1/` (`run.kaem` is the one line `/bin/sh /initrd/steps/run.sh`), the tarball below, timeout 24 h, out `artifacts/`.

## The source tree (`gcc1/excludes`)

`tar xf gcc-4.6.4-c0d20242.tar -X gcc1/excludes` into `/build/gcc-src`. tar 1.12's `-X` patterns with `*` are `fnmatch()`ed with `FNM_LEADING_DIR`, `*` also matching `/`; a pattern without wildcards only matches the member of that exact name, so every directory is excluded as `DIR/*` (its empty directory stays). Left out (nothing a C-only `--disable-bootstrap` build reads):

- `gcc/testsuite`, `gcc/ada`, `gcc/cp`, `gcc/fortran`, `gcc/go`, `gcc/objc`, `gcc/objcp` (front ends other than C; the C++ front end comes back in phase 4);
- `libjava`, `libgo`, `libgfortran`, `libobjc`, `libada`, `gnattools`, `libstdc++-v3`, `boehm-gc`, `libffi`, `libgomp`, `libmudflap`, `libquadmath`, `libssp`, `lto-plugin`;
- `gcc/po/*.po`, `libcpp/po/*.po` (message catalogues; `--disable-nls`);
- `pax_global_header` (`git archive`'s pax global header, typeflag `g`; tar 1.12 would write it as a file).

`gcc/java` stays (43 files, 1.8 MB), though the plan lists it. The top-level `configure` turns off the target libraries of a language only when it reads that language's `gcc/LANG/config-lang.in` and the language is not enabled (`target_libs`); java's are `target-libffi target-zlib target-qthreads target-libjava` (`libgcj`), and `zlib/` is in the tree (cc1 links the host zlib). Without `gcc/java` the run built libgcc and then configured `target-zlib` with xgcc: `checking dynamic linker characteristics... configure: error: Link tests are not allowed after GCC_NO_EXECUTABLES.`, `make[1]: *** [configure-target-zlib] Error 1`. With it `TARGET_CONFIGDIRS` is `libgcc` alone, as for a C-only build of the release tarball. Every other language left out also has its target libraries left out (`cp` → `libstdc++-v3`, `fortran` → `libgfortran`, `go` → `libgo`/`libffi`, `objc` → `libobjc`, `ada` → `libada`/`gnattools`). gcc's own `configure` then also reads java's `lang.opt`, `Make-lang.in` and GC roots (more options in `options.h`, `gt-java-*.h` from gengtype), as with the release tarball; nothing of java is built.

Kept: 3 505 files, about 105 MB (`gcc/` 2 360 files of which `gcc/config` 1 571; `libgcc`, `libiberty`, `libcpp`, `libdecnumber`, `zlib`, `intl`, `fixincludes`, `include`, `config`, `contrib`, `gcc/doc`). Extracting takes 6–8 s.

tar 1.12 does not read the POSIX ustar `prefix` field. The 125 members whose path is longer than 100 bytes (all in `libjava/` and `libstdc++-v3/`, excluded) come out at the top of the tree under their last name (`DemoServant.java`, `2.cc`, `constructors_destructor_fn_imps.hpp`, a directory `explicit_instantiation`, …); `run.sh` removes them (`rm -rf explicit_instantiation *.cc *.class *.css *.h *.hpp *.html *.java`; the top of the git tree has no such files). Phase 4 needs `libstdc++-v3`, and 7 of these are its `include/ext/pb_ds/detail/` headers: rung gcc4 extracts them again with its own ustar reader (`gcc4/src/ustar-x.c`, below).

`gengtype-lex.c` (not in git) is generated by our flex 2.6.4 inside `make`, `options.c`/`options.h` by gawk 3.0.4 (the same bytes as a host awk, checked on the host).

## Patches (`gcc1/patches/`, `patch -p1` in `/build/gcc-src`, in name order)

1. `native-system-header-dir.patch` (`gcc/Makefile.in`): restores `NATIVE_SYSTEM_HEADER_DIR = /usr/include` (upstream 4.6.4's line; the fork comments it out, its only change to that file: Guix has no `/usr/include` and passes `C_INCLUDE_PATH`) and adds `-DNATIVE_SYSTEM_HEADER_DIR=\"$(NATIVE_SYSTEM_HEADER_DIR)\"` to `PREPROCESSOR_DEFINES` (`cppdefault.o`), as GCC 4.7 does. The fork's musl `INCLUDE_DEFAULTS` (`gcc/config/linux.h`, from 4.7) take `/usr/include` only from that macro, which 4.6's Makefile never defines. Guest error without it, first libgcc file: `tsystem.h:87:19: fatal error: stdio.h: No such file or directory` (xgcc searched only `/usr/gcc1/include`, `/usr/gcc1/riscv64-unknown-linux-musl/include` and its own `include`). The plan's `--with-native-system-header-dir=/usr/include` does not exist in 4.6's `configure` (added in 4.7) and is not passed.
2. `riscv-ucontext.patch` (`gcc/config/riscv/linux-unwind.h`): `struct ucontext uc;` → `ucontext_t uc;`. musl has only `ucontext_t` (`typedef struct ucontext_t {…}`). Guest error without it: `config/riscv/linux-unwind.h:45:21: error: field 'uc' has incomplete type` (libgcc's `unwind-dw2.c`). Ekaitz's `commencement.scm` makes the same substitution for `gcc-muslboot0` (phase `patch-for-modern-libc`).
3. `ssa-operand-alloc.patch` (`gcc/tree-ssa-operands.c`): Ekaitz's commit `dc7a8963b8` as it is (blog series "Bootstrapping GCC in RISC-V", post 14; report [tinycc-devel 2024-04 msg00027](https://lists.nongnu.org/archive/html/tinycc-devel/2024-04/msg00027.html)). In `ssa_operand_alloc()` the index `gimple_ssa_operands (cfun)->operand_memory_index` goes through a local `int x` before `&(…->operand_memory->mem[x])`: tcc mob of 2024-04 on riscv64 miscompiled `&(f()->mem[f()->index])` with an inline `f` (the reproducer segfaulted). Our tcc (mob `e23dabed` + stage 11) builds the reproducer right: `gcc1/tests/ssaidx.c`, compiled by tcc on the guest, prints `tcc ssaidx ok`, and the host cross tcc of the same sources keeps the first `obtain()` result in a stack slot across the second call. The patch stays as the plan asks; it can be dropped later.

No other source change. GCC warnings from tcc (host rehearsal, all of `all-gcc`): no implicit declarations; `cast between pointer and integer of different size` in libiberty's non-GNU `obstack_free` macro and similar, "function might return no value", one real fork slip in `riscv.c:2241` (`riscv_flatten_aggregate_field`: `tree elt_size` gets `GET_MODE_SIZE (…)` in the `COMPLEX_TYPE` case and is compared with `UNITS_PER_FP_ARG`; harmless, the pointer holds the small integer).

   ```
   /bin/sh /build/gcc-src/configure --prefix=/usr/gcc1 \
     --build=riscv64-unknown-linux-musl --host=riscv64-unknown-linux-musl --target=riscv64-unknown-linux-musl \

     --disable-libmudflap --disable-libssp --disable-libgomp --disable-libquadmath --disable-lto \
     --disable-decimal-float --disable-threads --disable-libstdcxx-pch \
     --with-gmp=/usr --with-mpfr=/usr --with-mpc=/usr --with-arch=rv64gc --with-abi=lp64d \
     CC="tcc -static" CC_FOR_BUILD="tcc -static" CFLAGS=-g0 CFLAGS_FOR_BUILD=-g0 \
     CFLAGS_FOR_TARGET="-O2 -g0" AR=ar RANLIB=ranlib MAKEINFO=true
   ```
   with `SHELL=CONFIG_SHELL=/bin/sh` and `LDFLAGS="-static -Wc,-static"` exported (rung gmp). Differences from the plan's line:
   - run as `/bin/sh configure`: Tilck's `execve()` of a `#!` script takes at most 32 arguments (12-tilck README, `USERAPP_MAX_ARGS_COUNT`); with 31 arguments plus the interpreter the first run stopped with `/build/gcc-src/configure: Argument list too long`. The Makefiles run every directory's `configure` with `$(SHELL)` themselves.
   - no `--with-native-system-header-dir` (not in 4.6; patch 1).
   - `CC="tcc -static"`: tcc-m without `-static` writes a dynamic executable (14-seed README); `gcc/` is not built by libtool, `CC` reaches every link, and `CC_FOR_BUILD` the generator programs.
   - `CFLAGS_FOR_TARGET="-O2 -g0"` (libgcc): with `CFLAGS=-g0` the top-level `configure` would set `-g -g0` (its two `case`s both start from `$CFLAGS`, the second drops the `-O2` the first added), i.e. an unoptimised libgcc; GCC means target libraries to be `-O2`.
   - `--with-arch=rv64gc --with-abi=lp64d`: these names are the fork's (`gcc/config.gcc`, `riscv*-*-*`: `supported_defaults="abi arch tune"`).

## Static linking

gcc-1 links dynamically by default like any GNU/Linux GCC (`LINK_SPEC` of `config/riscv/linux.h`: `-dynamic-linker /lib/ld-musl-riscv64.so.1` unless `-static`), and Tilck refuses a dynamic executable; there is no `libc.so` either. Decision: no specs change; every link says `-static` (the tests, and the next rungs through `CC`/`LDFLAGS`, as with tcc-m). A specs file in `/usr/gcc1/lib/gcc/…/specs` would not help phase 3 anyway: the stage 2 and 3 compilers of `make bootstrap` use their built-in specs.

## Generator check

The 25 files written by the generator programs (`insn-*.c`, `insn-*.h`, `insn-conditions.md`, `tm-preds.h`, `tm-constrs.h`, `genrtl.h`, `gtype-desc.[ch]`, `tree-check.h`, `options.h`) were compared with a host rehearsal of the same tree (generators built by clang on macOS, `@SRC@` for the source path). 23 are byte-identical. The two others differ for reasons outside tcc:

- `insn-conditions.md`: `gencondmd.c` evaluates the md conditions with `__builtin_constant_p` only `#if GCC_VERSION >= 3001`; tcc does not define `__GNUC__`, so it marks none as constant. Every file derived from it is identical anyway.
- `insn-automata.c`: `genautomata` sorts states with `qsort()` by comparators that return 0 for ties (`compare_transition_els_num`), so the order follows the C library's `qsort`. The host `genautomata` linked with musl 1.1.24's `qsort.c` writes exactly the guest's file (`8e316c9c…`).

### Root cause: Tilck's mmap side, not tcc

Both crashes (gcc-1 on stage 1's `fold-const.c` at `-O1`; stage 1, built by gcc-1 at `-O0`, on `unwind-dw2.c` at `-O2 -g`) came from three bugs of Tilck's `munmap()`/`mremap()` (12-tilck README, plan 5 phase 3; tests `munmapspan ok`, `munmappart ok`, `mremap ok`), which corrupted the heap of any big cc1 run. How it was found (host-only diagnostics under `/tmp`, one QEMU at a time, nothing in the repo or artifacts):

- gcc-1's cc1 and a cc1 built on the host from the same configured tree by the host cross tcc (`/tmp/g464/hb3`) both crash on stage 1's `fold-const.i` (sha256 `6c83bc8a…6326`) at `-O1` under Tilck; so does a cc1 linked from the same 327 `gcc/` objects compiled from tcc's preprocessed sources by `riscv64-elf-gcc` 16.2 at `-O0`, with libiberty, libcpp, libdecnumber, zlib and gmp/mpfr/mpc also rebuilt by gcc 16: no tcc-compiled code left but libtcc1's helpers, yet `internal compiler error: in ?, at tree.c:5245` (`lookup_attribute`) or `Segmentation fault`, varying with the link. A clang-built x86_64 cross cc1 of the same tree compiles the file (7 s).
- The same all-gcc cc1 with `malloc`/`calloc`/`realloc`/`free` replaced (`ld --wrap`) by a bump allocator over one 3 GB `mmap()` (no reuse, freed blocks poisoned or not) compiles it: GCC used no freed memory; the heap under it broke. A frame-pointer backtrace from a wrapped `internal_error()` and the saved user registers put the fault in `obstack_free` ← `bitmap_obstack_release` ← `remove_preds_and_fake_succs` ← `solve_constraints` (the `ealias` pass).
- Small programs on Tilck: two adjacent `mmap()`s and a `munmap()` across both, then a new `mmap()` that returned the first one's live head; random `mmap()`/partial `munmap()` with overlaps between live blocks; a random `malloc`/`realloc`/`calloc`/`free` stress of musl that died of SIGSEGV (the same stress built for macOS passes). Tracing musl's `__mmap`/`__munmap`/`__madvise`/`__mremap`/`__expand_heap` showed the last call before the crash: `mremap(…, 0x276000, 0x10000)` → `-1`, after which musl 1.1.24's `realloc()` copies the old 2.5 MB into a new 64 KB block.
- With the three fixes: gcc-1's cc1 and the host-tcc cc1 compile `fold-const.i` at `-O1` (308 s and 167 s), the stresses pass, `tilck.py --test` is green.

The rootfs artifacts stay valid (kernel-only fixes): rung gcc1 on the fixed kernel gives `rootfs-gcc1.tar` sha256 `21bcb7ae…0439` again, rung musl2 `rootfs-musl2.tar` `8a13fc3c…0f82` again (both byte for byte as before).

### Fixed point: what differed and why

gcc-3's and gcc-4's cc1 compiled the same 71 GCC sources with the same driver and flags; 18 came out different: `combine`, `expr`, `reload`, `sel-sched`, `cse`, `var-tracking`, `optabs`, `varasm`, `tree-cfg`, `tree-inline`, `emit-rtl`, `haifa-sched`, `tree-data-ref`, `cfgexpand`, `ipa-inline` at `-O1`, `combine`, `expr`, `cse` at `-O2`. Examples: in `combine.c` gcc-3 makes `x*41` with `sll 3`, `sll 5`, `add`, `add`, gcc-4 with `li 41`, `mul`; in `reload.c` other registers. Rung gcc3's `Comparison successful` holds for stage 2 against stage 3, which are built the same way, so it could not see this.

How it was found (scratch diagnostic boots on `rootfs-gcc3.tar`, one QEMU at a time, scripts and results under `/tmp`, nothing in the repo or artifacts; each configured GCC's tree as rung gcc4 does):

1. Not the kernel, not nondeterminism: each cc1 gives the same assembly twice and with a 64 KB environment and a longer argv (combine.c, a small test); anonymous `mmap()` after `munmap()` of dirtied pages and `calloc()` after `free()` of dirtied blocks come back zeroed (50 rounds, 7 sizes up to 3 MB; 200 calloc rounds).
2. The two cc1s were not built alike. gcc-4's `gcc/` was compiled at `-O0` (gcc/configure's `-O` removal, run.sh step 5), gcc-3's at `-O1` (`BOOT_CFLAGS`). Their RTL dumps number the same patterns differently (`jump` 204 against 214): `gencondmd`, built at `-O1`, folds the one condition `(!TARGET_64BIT) && (TARGET_64BIT)` to 0 and gensupport drops those 10 impossible patterns; built at `-O0` it folds none of the 60 conditions.
3. Those 10 patterns did not matter: a gcc-4 cc1 built at `-O0` with stage 3's `insn-conditions.md` still differed from gcc-3 exactly as gcc-4 did. The same tree with `gcc/` at `-O1` gave gcc-3's output on all 5 files tried. So the level at which cc1 itself was compiled changed what cc1 produced.
4. Bisection over the 327 objects of `gcc/` (cc1 linked from `-O1` objects with a subset at `-O0`): `insn-modes.o` alone gives the `-O0` behaviour. Its tables (mode class, size, precision, mask, wider, inner, alignment, …) have the same contents at `-O0`, `-O1` and `-O2`, dumped by a test program linked with each object; only their order differs (`-O0` keeps source order, `-O1` reverses it). `insn-modes.o` at `-O1 -fno-toplevel-reorder` gives the `-O0` behaviour, at `-O1 -fno-merge-constants` the `-O1` one: the order of the tables decides.
5. A cc1 with every `machmode.h` accessor (`GET_MODE_CLASS`, `GET_MODE_SIZE`, …, `GET_CLASS_NARROWEST_MODE`) checking its index reported, for every file compiled, indexes 49, 51, 52, 55 and 59 against 41 modes, all at `config/riscv/riscv.c:1417` (`FLOAT_MODE_P (mode)`), `:1553` and `:1559` (`GET_MODE_SIZE (mode)` for PLUS and MULT), nowhere else (and nothing from the generators).

Root cause: the fork's `riscv_rtx_costs` has a later GCC's signature, `(rtx x, machine_mode mode, int outer_code, …)`, while GCC 4.6 calls `targetm.rtx_costs (x, code, outer_code, &total, speed)` (`rtlanal.c`, `rtx_cost`). The rtx code (PLUS, MULT, the shifts, the comparisons) was taken for the mode and used as an index into `mode_class[]` and `mode_size[]`: the costs of additions, multiplications and shifts came from whatever table the linker put after them. Every cc1 of the fork has this bug, gcc-1 and gcc-3 too; which costs a cc1 got depended on how `insn-modes.c` was compiled. The other target hooks `riscv.c` defines match the argument lists of 4.6's `target.def` (those 4.6 does not have, such as `TARGET_LEGITIMATE_CONSTANT_P`, are unused).

Fix: `gcc3/patches/riscv-rtx-costs.patch` (rungs gcc3 and gcc4): the hook takes 4.6's `int code` and `mode = GET_MODE (x)`, as 4.6's `mips_rtx_costs`, which this port follows. Checked before the reruns in a diagnostic boot: the instrumented cc1 reports no out-of-range index on `cse.c`, `combine.c`, `expr.c`, `reload.c` and a small test; with `insn-modes.o` in either table order the assembly of all five is the same; it differs from the unpatched gcc-3 (`reload.c` 323 lines), so gcc-3 had to be rebuilt: rung gcc3 run 6 (above). gcc-1 and musl-2 stay: gcc-1 only compiles stage 1 and musl, and its odd costs give other, still correct code. The layout test of step 8 keeps it from coming back: gcc-3 and gcc-4 are now both built with the tables reversed (`-O1`, `-O2`), so the fixed point alone would no longer see a layout dependence.
