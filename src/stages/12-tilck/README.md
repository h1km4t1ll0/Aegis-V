# 12 — Tilck (riscv64 kernel built by the guest)

Inside QEMU, Kronos runs `/bin/tcc7b` (stage 11) to install the Linux uapi headers, generate Tilck's config headers, compile every Tilck kernel file plus libfdt, and link `/build/tilck/tilck.elf`. The host only plants files from the pinned archives and the files of this stage, then copies the ELF the guest announces (`snap tilck ADDR SIZE`) to `artifacts/tilck.elf`. It also builds our M-mode SBI shim (`src/sbi/`, copied to `artifacts/sbi.bin`); `src/scripts/tilck.py --boot` boots both in a fresh QEMU (see Boot).

## KFS layout (`collect_kfs_tilck()`)

- `/src/uapi/<archive path>`: every `.h` of the uapi archive; `/src/uapi/FILES` lists them (Kronos has no `getdents`).
- `/src/tilck/<archive path>`: Tilck's `include/`, `kernel/`, `common/`, `config/`, `modules/{console,serial,riscv_irq,goldfish,null,sysfs,tracing}/`, with `src/override/` on top (it adds `modules/outbox/`); `/src/tilck/libfdt/*.{c,h}` from dtc. `/src/tilck/CONFIG_FILES` (`config/*.h`, `config/kernel/*.h`) and `/src/tilck/MODULES` (all `modules/*` directories) are tar listings.
- `/src/tilck/{tilck-config.txt,cflags.rsp,SOURCES,link.rsp}`, `/src/tilck/sbi/{sbi.rsp,sbi-entry.s,sbi.c}`, `/src/tilck-tools/{headers-install,gen-tilck-config}.c`, `/src/tilck-tests/*` (every file of `tests/`).

`kronos.py` prints the size of `ramfs.bin` and stops if it is over `0x3E00000`.

## Guest steps (`09-kronos/src/kmain.c`, after `t7 done`)

1. `/bin/headers-install` (`src/headers-install.c`): `make headers_install` of Linux v6.6 without sed. Applies the sed rules of `scripts/headers_install.sh` (drop `__user`/`__force`/`__iomem` and `__attribute_const__`, drop `#include <linux/compiler.h>`/`<linux/compiler_types.h>`, `__packed`, `__inline__`/`__asm__`/`__volatile__`, `_UAPI` guards) and its `unifdef -U__KERNEL__ -D__EXPORTED_HEADERS__` for the plain `#ifdef`/`#ifndef`/`#if [!]defined()` forms; arch files go on top of the generic ones; each `asm-generic/X.h` without an arch `asm/X.h` gets `/usr/include/asm/X.h` = `#include <asm-generic/X.h>`. UART `headers-install built`, then `tests/uapi-check.c` prints `uapi ok`.
2. `/bin/gen-tilck-config` (`src/gen-tilck-config.c`, values in `src/tilck-config.txt`): CMake's `configure_file(@ONLY)` of `config/*.h` → `/build/tilck/tilck_gen_headers/` and `config/kernel/*.h` → `/build/tilck/kbin/tilck_gen_headers/`, `modules_config.h` (root `CMakeLists.txt`) and `generated_config.h` (what `scripts/build_apps/gen_config.cpp` writes: the sysfs config objects and `sysfs_create_config_obj()`, which `modules/sysfs/sysfs.c` calls). A name that `tilck-config.txt` does not list, as `NAME=value` or in `ON=`/`OFF=`, is an error. Prints `tilck config ok`.
3. `build_objs("/src/tilck/SOURCES", "@/src/tilck/cflags.rsp", "/src/tilck/", "/build/tilck/obj/", "tilck")` (stage 13 builds musl with the same loop): one `/bin/tcc7b @/src/tilck/cflags.rsp -I <dir> -c <src> -o /build/tilck/obj/<path with / → __>.o` per `SOURCES` line (Tilck has three `misc.c`). Each failure prints `tilck obj fail <path>`; when all objects exist: `tilck objs ok`.
4. `/bin/tcc7b @/src/tilck/link.rsp` → `/build/tilck/tilck.elf`, UART `tilck linked` and `snap tilck ...`.
5. `/bin/tcc7b @/src/tilck/sbi/sbi.rsp` → `/build/tilck/sbi.bin`, UART `sbi built` and `snap sbi ...`.
6. The initrd programs, each `/bin/tcc7b -o /build/tilck/X -I /include -nostdlib -static -Wl,-Ttext=0x10000 -Wl,-oformat=elf64-little /src/tcc7/compat-crt.s /lib/libc.c SRC` (`t7_cc()`): `init` from `/src/tilck/init.c`, `proc` and `child` from `/src/tilck-tests/`. UART `tilck progs built` and `snap tinit|tproc|tchild ...`; `kronos.py` copies them to `artifacts/{init,proc,child}.elf`. Then `tilck done`.
7. In stage 13's `build_musl()`, after musl: `tests/mem.c` → `/build/tilck/mem` and `tests/hard.c` → `/build/tilck/hard` with `musl_cc()` (UART `musl progs built`, `snap tmem`, `snap thard`); `kronos.py` copies them to `artifacts/mem.elf` and `artifacts/hard.elf`.

  - Shared open file descriptions (plan 4 phase 3, found by rung build1: `(echo aaaa; echo bb) > f` gave `bb` + the rest of `aaaa`'s line, every `config.log` was fragments; test `tests/hard.c` `sharedoff ok`). Tilck gave each fd of a `fork()` child and each `dup()`/`dup2()`/`F_DUPFD` a copy of the handle, with its own offset. Now, as Linux's `struct file`, they share one handle: `include/tilck/kernel/fs/vfs_base.h` adds `h_refs` to the handle base, `kernel/vfs/vfs.c` sets it to 1 in `vfs_create_new_handle()`, `vfs_dup()` only retains the handle (no copy, so the fs `on_dup_cb`s are no longer called), and `vfs_close()` frees the handle (the fs `on_close`, inode, lock and fs releases) only when the last reference goes; the process's mappings of the handle are removed when its last fd of the handle is closed (was: at every close of a copy). `kernel/fork.c` `fork_dup_all_handles()` retains each handle (it cannot fail now) and no longer re-points the child's mappings. FD_CLOEXEC belongs to the fd, not to the shared handle: `include/tilck/kernel/process.h` adds `u8 fd_flags[KRN_MAX_HANDLES]` at the end of `struct process` (copied by `fork()`), and `kernel/fs/fs_syscalls.c` sets it when an fd is installed (`open` from `O_CLOEXEC`, `dup2` 0, `pipe2` from `O_CLOEXEC`), uses it in `close_cloexec_handles()` and `F_GETFD`/`F_SETFD`, and `F_DUPFD_CLOEXEC` now sets it (upstream tested `sys_dup2()`'s result, the new fd, for 0, so the flag was never set). `kernel/arch/riscv/process_riscv.c`: the `task_and_process` bound + `KRN_MAX_HANDLES` bytes. `kernel/mm/process_mm_base.c` `generic_fs_munmap()` unmaps in the mapping's process (`um->pi`), not the handle's opener (`hb->pi`, which a shared handle no longer identifies).
  - `kernel/signal.c` (plan 4 phase 3, found by rung build1: gawk's `abort()` in its SIGSEGV handler hung the process; test `tests/hard.c` `abort ok`): Tilck runs no signal handler inside another, and `process_signals()` returned at once while a handler ran, so the SIGABRT that `abort()` raises there stayed pending, and musl's final `a_crash()` store to address 0 faulted forever. Now, while a handler runs, a pending unmasked signal whose action is the default (terminate) or one raised by a fault kills the task, as Linux does (signals with handlers still wait for `sigreturn`). `get_first_pending_sig()` takes the first pending signal that is not masked (it looked only at the lowest pending bit of each word and gave up if that one was masked).

## Memory

QEMU `-m 8G`: RAM is `0x80000000`–`0x280000000`. `LINEAR_MAPPING_MB=8192` maps all of it at `BASE_VA` (`0x2000000000`–`0x2200000000`); the hi vmem area (128 MB) follows at `0x2200000000` (`HI_VMEM_START` override), and Sv39's lower half ends at `0x4000000000`, so the layout has room for more. Taken from RAM: the SBI shim and Tilck's DTB copy (2 MB), the kernel (~1 MB), the initrd, the outbox region (1 GB by default, the top of RAM); the rest (about 7 GB with a small initrd) is Tilck's kmalloc memory, shared by the kernel and user pages (Tilck log: `System memory map from multiboot`). A user process has brk up to `0x40000000` and an mmap area from there that doubles from 16 MB up to 8 GB (`USER_MMAP_MAX_SZ`); `tests/mem.c` maps, fills and frees 3 GB in one `mmap()`.

## Kernel stack

Plan 3 saw one hang, during the rootfs unpack of rung tools2: an S-mode trap loop (`scause` 0xf, store page fault, at the trap entry's `sd ra, 8(sp)`, with a garbage `sscratch`/kernel `sp`), which looked like a kernel stack overflow. `KERNEL_STACK_PAGES` is now 16 (64 KB per task, was 4); with `KRN_STACK_ISOLATION` the 64 KB below each stack stay unmapped (was one 4 KB guard page). An overflow into the guard faults, and the trap entry's first store on the same `sp` faults again: the loop plan 3 saw, which is why it looked like an overflow. The hang was not reproduced: rung tools2 ran green five times in a row with the guest-built 16-page Tilck, and, as `/tmp` diagnostics (not in the repo), once with a host-built 16-page copy and four times with a host-built copy of the old 4-page configuration, both with two probes: at each task's exit the deepest non-zero word of its (zeroed) kernel stack, and at every IRQ and fault entry the stack depth. The deepest task stack seen was 3.9 KB (3.4–3.9 KB in every run, also with 4 pages), and no IRQ or fault entry came above 6 KB, so the normal tools2 load uses under a quarter of the old 16 KB: an overflow is not confirmed, the cause of that hang is unknown. If it happens again: `info registers` over QMP (`sscratch`, `sp`, `sepc`, `stval`) and the stack depth probes above. It happened again in plan 4 phase 3 (rung binutils, `make` in `ld/`), and this time the overwritten memory and the task's kernel stack (QMP `x`) showed the cause: not an overflow but tcc's function epilogue, which read the saved `ra`/`s0` below `sp` after giving the frame back; a timer interrupt in that window wrote the trap frame's `sscratch` slot (0) over the saved `s0`. Fixed in tcc (11-tcc7 README, `riscv64-gen.c` `gfunc_epilog()`, test `epilog.c`); Tilck, musl and the seed are rebuilt with it.

## Outbox (`/dev/outbox`)

- Host → guest: `tilck.py` puts `OUTBOX_ADDR`/`OUTBOX_SIZE` (default `0x240000000`, 1 GB: the top of RAM; both 2 MB aligned) in the bootinfo; the shim adds `/reserved-memory/outbox@240000000` (`no-map`); Tilck's memory map shows it as reserved (type 2), so kmalloc never uses it.
- Guest: `modules/outbox/outbox.c` finds the node, maps the region RW at kernel VA `0x3000000000` (the linear mapping maps reserved memory read-only) and creates the char device `/dev/outbox` (dynamic major; log `outbox: 0x240000000, 1024 MB`). `write()` appends (one stream per boot, never reset; a write past the end is short, then `-ENOSPC`; `O_TRUNC` is ignored, so `fopen("w")` and shell `>` work); `read`/`seek` are not supported. Every `close()` of a handle prints `outbox 0x240000000 <total bytes written since boot>`.
- Host: `tilck.py` sees each `outbox ADDR SIZE` line and a worker thread copies the first SIZE bytes of the region to `artifacts/outbox.bin` (QMP `pmemsave` in 64 MB chunks to `outbox.bin.chunk`, then `outbox.bin.part` → `outbox.bin`), while the UART keeps draining; it prints `[outbox] … bytes from 0x240000000 in …s sha256 …`. Before stopping QEMU it waits for the dumps (up to 600 s). For a big result write it once and close once: each close triggers a full dump of everything written so far.
- Checked once beyond the gate (`/tmp` diagnostic, not in the repo): a 700 MB initrd (`bin/child` padded to 734 052 004 bytes, image end `0xBBD0E000`, past the old `0xB8000000` limit) with the same `--test` flow: `proc` copied the whole file through `/dev/outbox`, the 734 MB dump took 2.8 s and the sha256 matched; the run took 8.5 min, most of it `proc`'s byte-at-a-time SHA-256 under TCG (the gate run with the small initrd: about 75 s, `mem` about 50 s of it).
